Görev: EF6 Database-First projede generic entity history/audit mekanizması tasarla ve uygula

1. Proje bağlamı

Mevcut proje:

• .NET Framework 4.8
• Entity Framework 6.0.0.0
• Database-First yaklaşımı kullanıyor.
• .edmx ve .edmx.diagram dosyaları mevcut.
• Entity’ler büyük ölçüde EDMX tarafından generate ediliyor.
• Mevcut veritabanında Agile/Jira benzeri bir yapı bulunuyor.
• Temel entity’ler:
  • Agile Epic
  • Agile Feature
  • Agile PBI
• Gerçek tablo/entity isimleri implementation sırasında mevcut projeden tespit edilmeli. Bu dokümanda örnek olarak:
  • AgileEpic
  • AgileFeature
  • AgilePbi
kullanılabilir.
• History tablosunun gerçek adı henüz kesin değil. Dokümanda [HistoryTable] placeholder olarak kullanılabilir.

İstenen özellik:

Epic, Feature ve PBI entity’lerinin bütün kolonlarını değil, belirli kolonlarının değişikliklerini tarihçe olarak kaydetmek.

History kaydı şu temel bilgileri içermeli:

• History record ID
• Entity type
• Entity ID
• Değişen field/property adı
• Eski değer
• Yeni değer
• Değişiklik tarihi
• Değişikliği yapan kullanıcı

Önerilen generic model:

```text
[HistoryTable]

Id
EntityType
EntityId
Field
OldValue
NewValue
ChangedAt
ChangedBy
```

EntityType örneğin:

```csharp
public enum AgileEntityType
{
    Epic = 1,
    Feature = 2,
    Pbi = 3
}
```

olabilir.

Ancak gerçek isimler mevcut projeye göre belirlenmelidir.

────────

2. ÖNEMLİ TASARIM KARARI

Epic, Feature ve PBI için üç ayrı generic history tablosu oluşturulmayacak.

Şu yapı tercih edilmeli:

```text
[HistoryTable]
```

tek history tablosu olacak ve:

```text
EntityType + EntityId
```

ile hangi entity’nin history’si olduğu belirlenecek.

Örnek:

```text
EntityType = Pbi
EntityId   = 123
Field      = Priority
OldValue   = 2
NewValue   = 3
```

ve:

```text
EntityType = Feature
EntityId   = 123
Field      = Title
OldValue   = Old Title
NewValue   = New Title
```

aynı tabloda bulunabilir.

Burada EntityId polymorphic reference olacaktır. Dolayısıyla generic history tablosunda klasik FK kullanımı mümkün olmayabilir. Bunun bilinçli bir tasarım kararı olduğu kabul edilmelidir.

────────

3. STATUS LOG’LARINI HISTORY İLE BİRLEŞTİRME

Mevcut sistemde:

```text
[AgileEpicStatusLog]
[AgileFeatureStatusLog]
[AgilePbiStatusLog]
```

benzeri status log tabloları bulunmaktadır.

Bunlar generic [HistoryTable] içine taşınmayacak.

Çünkü bunların amacı generic field audit’ten farklıdır.

Status log’larda örneğin:

```text
Id
BusinessStatus
Date
CreatedBy
```

bulunmaktadır.

PBI status log’unda ayrıca:

```text
Explanation
```

alanı bulunmaktadır.

Dolayısıyla status log’lar domain’e özgü status lifecycle bilgisidir.

History tablosuna:

```text
Status: OldStatus -> NewStatus
```

şeklinde tekrar yazılmamalıdır.

Böylece aynı status değişikliğinin hem status log hem generic history tablosunda duplicate edilmesi engellenmelidir.

Mevcut status log yapısına bu çalışma kapsamında mümkün olduğunca dokunulmayacak.

4. EN ÖNEMLİ IMPLEMENTASYON KARARI

Business kodunun her değiştirdiği property için manuel olarak:

```csharp
historyRepository.Create(...)
```

çağırması İSTENMİYOR.

Örneğin şu yaklaşım kullanılmamalı:

```csharp
pbi.Title = request.Title;

historyRepository.Create(...);

pbi.Priority = request.Priority;

historyRepository.Create(...);

pbi.StoryPoint = request.StoryPoint;

historyRepository.Create(...);
```

Bu yaklaşım özellikle büyük projede history oluşturmayı developer’ın unutmasına neden olur.

Bunun yerine:

```text
Business code
      ↓
Entity property değişikliği
      ↓
EF6 ChangeTracker
      ↓
SaveChanges / SaveChangesAsync
      ↓
History builder
      ↓
[HistoryTable]
```

mekanizması kurulmalıdır.

6. DATABASE-FIRST / EDMX UYUMLULUĞU

EDMX tarafından generate edilen dosyalar doğrudan elle değiştirilmemeli.

Örneğin:

```text
[Something].Designer.cs
```

gibi generated dosyalara history business logic eklenmemeli.

Çünkü EDMX yeniden generate edildiğinde değişikliklerin kaybolma riski vardır.

Bunun yerine mümkün olduğunca:

```text
partial class
```

kullanılmalı.

Örneğin generated context:

```csharp
public partial class ExistingDbContext : DbContext
{
}
```

ise ayrı bir dosyada:

```text
ExistingDbContext.History.cs
```

gibi:

```csharp
public partial class ExistingDbContext
{
    ...
}
```

kullanılabilir.

Ancak generated context’in mevcut yapısı mutlaka incelenmeli.

Eğer generated context içerisinde zaten SaveChanges override edilmişse, ikinci bir override oluşturulamayacağı için mevcut implementasyon buna göre genişletilmelidir.

Ama generated .Designer.cs dosyası değiştirilmemelidir.

9. ENTITY TYPE

Generic history’nin entity türünü belirlemek için enum kullanılmalıdır.

Örneğin:

```csharp
public enum AgileEntityType
{
    Epic = 1,
    Feature = 2,
    Pbi = 3
}
```

Enum değerleri DB’deki EntityType kolonuyla uyumlu olmalıdır.

Entity type resolution için aşağıdaki gibi güvenli bir mapping tercih edilmelidir:

```csharp
private static AgileEntityType? ResolveEntityType(object entity)
{
    switch (entity)
    {
        case AgileEpic:
            return AgileEntityType.Epic;

        case AgileFeature:
            return AgileEntityType.Feature;

        case AgilePbi:
            return AgileEntityType.Pbi;

        default:
            return null;
    }
}
```

Reflection ile:

```csharp
entity.GetType().Name
```

üzerinden string manipulation yaparak enum bulmaya çalışma.

Örneğin:

```text
AgilePbi -> Pbi
```

gibi string convention’a güvenilmemeli.

Yeni entity eklendiğinde mapping’in explicit olarak güncellenebilmesi tercih edilmeli.

10. HANGİ FIELD’LAR HISTORY’YE GİRECEK?

Bütün property’ler audit edilmeyecek.

Örneğin:

```text
Title             -> YES
Description       -> YES
Priority          -> YES
StoryPoint        -> YES
Assignee           -> YES

Id                -> NO
CreatedAt         -> NO
CreatedBy         -> NO
UpdatedAt         -> NO
UpdatedBy         -> NO
RowVersion        -> NO
Navigation props  -> NO
```

Gerçek field listesi mevcut requirement’a göre oluşturulmalıdır.

Bu bilgi ChangeTracker’a hard-coded şekilde dağılmamalı.

Central bir policy/mapping oluşturulmalı.

Örneğin:

```csharp
public class AgileHistoryFieldPolicy
{
    public bool ShouldTrack(
        AgileEntityType entityType,
        string propertyName)
    {
        ...
    }
}
```

veya mevcut proje için daha uygun başka bir yapı kullanılabilir.

Önemli olan:

> Audit edilecek alanların merkezi ve açık bir whitelist olması.

Blacklist yaklaşımı:

```text
Her şeyi history'ye al
sonra CreatedAt, UpdatedAt vb. çıkar
```

yerine whitelist tercih edilmeli.

Bu daha güvenlidir.

Yeni bir entity property eklendiğinde yanlışlıkla audit kapsamına girmemelidir.

13. OLD VALUE / NEW VALUE

Değerler DB’ye yazılmadan önce güvenli ve deterministik şekilde string’e çevrilmeli.

Basit:

```csharp
value?.ToString()
```

yaklaşımının bütün tiplerde güvenli olup olmadığı değerlendirilmelidir.

Özellikle:

```text
DateTime
DateTime?
Decimal
Enum
Boolean
Guid
Nullable<T>
```

gibi tipler düşünülmelidir.

Culture-dependent dönüşümlerden kaçınılmalı.

Örneğin decimal için:

```text
10.5
```

veya projenin belirlediği invariant format kullanılmalı.

DateTime için ISO/invariant format tercih edilmeli.

Enum değerlerinde sistemin istediği temsil belirlenmeli:

```text
1
```

mi yoksa:

```text
InProgress
```

mi?

Bu karar açıkça verilmelidir.

History’nin UI’da gösterileceği düşünüldüğünde mümkünse okunabilir değerlerin saklanması değerlendirilebilir; ancak DB’deki mevcut domain davranışı bozulmamalıdır.

16. SAVECHANGES OVERRIDE

Ana mekanizma DbContext.SaveChanges() içerisinde çalışmalı.

Örnek conceptual akış:

```csharp
public override int SaveChanges()
{
    var histories = historyBuilder.Build(ChangeTracker);

    AddHistories(histories);

    return base.SaveChanges();
}
```

Ancak gerçek implementasyonda recursive SaveChanges oluşturulmamasına dikkat edilmeli.

Özellikle:

```text
HistoryRepository.Add()
    ↓
SaveChanges()
    ↓
HistoryBuilder
    ↓
HistoryRepository.Add()
    ↓
...
```

şeklinde recursion kesinlikle olmamalı.

History kayıtları aynı DbContext’in:

```csharp
DbSet<AgileHistory>.Add(...)
DbSet<AgileHistory>.AddRange(...)
```

mekanizmasıyla context’e eklenmeli ve en sonunda tek base.SaveChanges() çağrılmalıdır.

────────

17. ASYNC SAVECHANGES

Projede SaveChangesAsync() kullanılıyorsa aynı history mekanizması async path’te de çalışmalıdır.

Örneğin:

```csharp
public override async Task<int> SaveChangesAsync(
    CancellationToken cancellationToken)
{
    var histories = historyBuilder.Build(ChangeTracker);

    AddHistories(histories);

    return await base.SaveChangesAsync(cancellationToken);
}
```

EF6 sürümünün mevcut async API desteği ve projenin kullandığı signature mutlaka kontrol edilmelidir.

SaveChanges() ve SaveChangesAsync() farklı davranmamalıdır.

18. REPOSITORY TASARIMI

History repository normal CRUD repository gibi tasarlanmamalıdır.

History:

```text
Append-only
```

olmalıdır.

Normal uygulama akışında:

```text
INSERT -> YES
SELECT -> YES
UPDATE -> NO
DELETE -> NO
```

Bu nedenle:

```csharp
CreateAsync(...)
GetByEntityAsync(...)
```

gibi operasyonlar yeterli olabilir.

Örneğin:

```csharp
public interface IAgileHistoryRepository
{
    Task<IReadOnlyList<AgileHistory>> GetByEntityAsync(
        AgileEntityType entityType,
        long entityId);

    Task<IReadOnlyList<AgileHistory>> GetByEntityAsync(
        AgileEntityType entityType,
        long entityId,
        DateTime? from,
        DateTime? to);
}
```

History insertion’ın normal business code tarafından manuel çağrılması gerekmemelidir.

History insertion’ın gerçek sahibi:

```text
SaveChanges history pipeline
```

olmalıdır.

Repository daha çok history okuma/query abstraction’ı olarak kullanılabilir.

19. TRANSACTION

Entity değişikliği ve history kaydı aynı transaction içerisinde gerçekleşmelidir.

İstenen davranış:

```text
BEGIN TRANSACTION

UPDATE PBI
INSERT History 1
INSERT History 2
INSERT History 3

COMMIT
```

Eğer history insert başarısız olursa entity update de commit edilmemelidir.

Aynı DbContext üzerinde aynı SaveChanges çağrısında yapılması bu konuda tercih edilmelidir.

20. CONCURRENCY

Mevcut projede optimistic concurrency / RowVersion kullanılıyorsa bunun history mekanizmasıyla ilişkisi değerlendirilmelidir.

History:

```text
OriginalValue
CurrentValue
```

üzerinden oluşturulsa bile SaveChanges sırasında concurrency exception oluşursa history kayıtlarının da transaction ile rollback olması gerekir.

Sonuç:

> Başarısız entity update için kalıcı history oluşmamalı.

Bu senaryo özellikle test edilmelidir.

────────

21. BULK UPDATE

Aşağıdaki EF6 tarzı işlemler varsa ayrıca incelenmeli:

```text
SqlQuery
ExecuteSqlCommand
Database.ExecuteSqlCommand
Stored Procedure
raw SQL UPDATE
```

Bunlar ChangeTracker üzerinden geçmeyebilir.

Dolayısıyla:

```text
Application üzerinden normal entity update
```

ile:

```text
Direct SQL update
```

aynı audit davranışına sahip olmayabilir.

Projede böyle kullanım varsa tespit edilmeli.

Eğer history’nin “uygulamadaki her DB değişikliğini kesinlikle yakalaması” şartı varsa ChangeTracker tek başına yeterli değildir.

Bu durumda database trigger / CDC / başka DB-level audit mekanizmaları ayrıca değerlendirilmelidir.

Ancak requirement yalnızca uygulama üzerinden yapılan entity değişikliklerini audit etmekse ChangeTracker yaklaşımı kullanılabilir.

27. PERFORMANS

Mevcut sistemde yaklaşık:

```text
120.000 Epic
130.000 Feature
3.700.000 PBI
```

bulunduğu bilinmektedir.

Bu sayı generic history tablosunu entity tipine göre üç ayrı tabloya bölmek için tek başına yeterli gerekçe değildir.

History tablosunun büyümesi beklenmektedir.

Bu nedenle öncelikle:

```text
Composite indexes
Efficient ChangeTracker filtering
Only whitelisted properties
Only actually modified properties
No unnecessary history rows
```

sağlanmalıdır.

İleride history row sayısı gerçekten çok büyürse:

```text
Partitioning
```

33. ÖNEMLİ TASARIM İLKESİ

Çözüm “çalışıyor” seviyesinde bırakılmamalı.

Şu anti-pattern özellikle kullanılmamalı:

```text
Her handler:
    entity değiştir
    history oluştur
    history oluştur
    history oluştur
```

Bunun yerine:

```text
Her handler:
    entity değiştir
    SaveChanges
```

ve audit mekanizması otomatik olarak:

```text
ChangeTracker
    ↓
HistoryBuilder
    ↓
History records
```

oluşturmalı.

Böylece history mekanizması business koduna dağılmaz.
